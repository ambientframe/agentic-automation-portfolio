### 12. Durable write-ahead observation accounting, reconciled rather than counted
- **Earned:** observation integrity package, 2026-08-26
- **Implementation:** `lib/persistence/observation-intent-store.ts` · `lib/observability/observation-integrity.ts` · `lib/observability/lead-rescue-journal.ts` (composition root)
- **Tests:** `tests/lead-rescue-observation-integrity.test.ts` (20 tests, RED before implementation; 8 targeted mutations each separately confirmed to fail it) · `tests/observation-integrity-evidence.test.ts` (20 tests, each confirmed to fail against a deliberately corrupted artifact)
- **Runtime artifact:** `n8n/evidence/lead-rescue-observation-integrity.json` — the journal directory was made unwritable for exactly one real HTTP ingress; the business path returned `200 ACCEPTED` and durably parked the case, the observation was genuinely lost, and the runtime named it: `CONFIRMED_DROP`, with the recorder's own `EACCES: permission denied, mkdir …` as the reason.
- **Establishes:** a lossy recorder can be held to account without becoming blocking. A marker naming the intended observation is written BEFORE the record, removed after a success, and annotated-and-left after a reported drop; a marker still outstanding is reconciled against the journal by `journalEventId`, so a crash in the cleanup window is not mistaken for data loss and a genuinely missing record cannot hide. The three answers stay distinct — `NO_KNOWN_LOSS`, `KNOWN_LOSS`, `UNAVAILABLE` — and an unreadable ledger or an unreadable journal both fail into the third rather than into the flattering first.
- **Why not a counter:** a process-local tally dies in exactly the crash it would need to survive, and reports a clean instrument at the moment the instrument is least trustworthy. The marker is durable, so the accounting outlives the process; `tests/lead-rescue-observation-integrity.test.ts` proves an unresolved intent survives a genuinely reconstructed store.
- **Limits (recorded, not hidden):** an observation whose marker ALSO failed to be written is invisible. That is why the clean answer is named `NO_KNOWN_LOSS` and never `COMPLETE`, why no completeness rate exists anywhere in the payload, and why the bound travels with every answer including the clean one. The `UNRESOLVED_INTENT` kind is test-proven; the retained capture exercises `CONFIRMED_DROP`.
- **Reusable for 2–6:** `withObservationIntegrity` decorates any `ExecutionJournalRecorder` and `deriveObservationIntegrity` reads any `ExecutionJournalReader`. Neither knows what a lead is.

### 14. A failure verdict that grants permission is earned structurally, never inferred from an error code
- **Earned:** execution-boundary classification package, 2026-08-26
- **Implementation:** `lib/ports/smtp-side-effect-executor.ts` — `SMTP_COMMANDS_BEFORE_DATA` plus the phase read in `attemptSend`'s catch
- **Tests:** `tests/smtp-side-effect-executor.test.ts` (39 tests, up from 17; 5 RED before implementation, and 5 targeted mutations of the shipped fix each separately confirmed to fail it — re-admitting the socket codes, adding `DATA` to the pre-DATA set, widening the syscall check, forcing the phase test true, and inverting the default)
- **Establishes:** `FAILED_BEFORE_EFFECT` is not a description of a socket, it is a **permission** — every layer above reads it as "nothing reached the recipient, a retry is safe." A permission may therefore only be issued where non-delivery is structural: a code that cannot follow DATA by protocol, a `connect` syscall, or an error raised against an SMTP command that precedes DATA. Everything else, including every unrecognised code and every error carrying no code at all, resolves to `OUTCOME_UNKNOWN` and parks for a person. The asymmetry is the point: a false uncertainty costs an operator one decision, a false certainty costs the customer a duplicate.
- **Why not a wider blocklist:** the first attempt routed every socket-class code to uncertainty. It was sound and it broke a genuine connection-refusal test, because nodemailer collapses connect-phase failures into `ESOCKET` — a real `ECONNREFUSED` arrives as `{code: 'ESOCKET', syscall: 'connect', command: 'CONN'}`. A blocklist that parks every refused connection trains an operator to clear a queue of decisions that were never theirs to make. Reading the phase the transport already reports is both sounder and more precise than either blanket rule.
- **The trap, recorded because it cost a full cycle:** a phase field is not necessarily a phase. nodemailer's `command: 'CONN'` marks a *connection-level* error whenever it occurs, not the connect phase — a server that takes the whole body and then destroys the socket reports `{code:'ECONNECTION', command:'CONN'}`, indistinguishable in shape from a greeting failure. Trusting it re-issued retry permission for exactly the case this pattern exists to stop, and 39 green unit tests did not notice. The re-captured runtime evidence did, on the first run. Before trusting any provider's phase field, probe it against the failure you actually fear.
- **Runtime artifact:** `n8n/evidence/lead-rescue-observation-integrity.json` — case D: the receiver holds 979 bytes and a stored message id, and the application records `OUTCOME_UNKNOWN` with verdict `DECLINED_TO_CLAIM`, parking the case rather than authorising a retry. Guarded by test 9b in `tests/observation-integrity-evidence.test.ts`, which ties each verdict to the bytes the receiver observed; 4 targeted corruptions each confirmed to fail it.
- **Limits (recorded, not hidden):** the phase is only as good as the transport's own reporting, *and* only as good as your understanding of what that reporting means. An adapter whose provider surfaces no trustworthy equivalent must fall back to the conservative rule and accept the extra uncertainty; it may not invent a phase.
- **Reusable for 2–6:** the shape generalises to every `SideEffectExecutor` any system adds. The question "does this failure prove non-execution, or merely suggest it?" is the same for a CRM write, an SMS gateway, and a calendar invite; only the phase evidence differs.

### 16. Identity resolution is the precondition for every policy check, not one check among them
- **Earned:** dp-fm-wrong-entity package, 2026-08-26

- **Establishes:** consent, account status, and commercial eligibility are all questions about a SPECIFIC party. Asking them against an identity nobody has established is meaningless work that reads as diligence, so identity resolves first and the handler returns immediately when it cannot. A match is accepted only on exactly one candidate at or above the configured threshold: two or more is the declared ambiguity, and zero is the same failure wearing a different face, because resolving it means taking the closest available match.

- **Limits (recorded, not hidden):** the guard only runs when the cycle supplies competing candidates. A record resolved upstream on a stable identifier has no ambiguity to decide, and manufacturing a decision for it would pad every run with a step that never chose anything — so a WRONG upstream resolution is invisible here. This bounds a match, it does not audit one.
- **Reusable for 2–6:** every system that matches an inbound artifact to an account has this shape — Lead Rescue on contact identity, Receivables on invoice identity, Client Onboarding on the signed party. Only the identifier differs.

### 18. A declared recovery is a claim about the transition graph, so ask the graph
- **Earned:** lifecycle-recovery package, 2026-08-26
- **Implementation:** `lib/model/system.ts` — `RecoveryPathSchema`, `RecoveryMoveSchema`, `describeRecovery`, and the recovery checks inside `validateLifecycle` · all 43 failure modes across `data/systems/**`
- **Tests:** `tests/lifecycle-recovery.test.ts` (12 tests; 8 RED before implementation, and 10 targeted mutations each separately confirmed to fail it — short-circuiting the check, disabling each of its three issue kinds, checking only the first movement of a multi-step recovery, dropping a marker so a defect reads as handling, inventing the missing transition, pointing a real recovery at an undeclared state, pointing one at a forbidden move, and stripping the defect wording from the rendered prose. None survived.)
- **Establishes:** a failure mode's `terminalState` was free prose, and a validator cannot check a sentence — which is exactly why two Dormant Pipeline recoveries sat for months declaring movements the engine would have refused. Replacing it with `{from, to}` pairs turns "where does this end up" from a description into a question the transition graph can answer, for every failure mode in every system.
- **Three shapes, because recoveries genuinely have three.** `MOVES` for an ordered list of movements; `HOLDS_POSITION` for the cases where not moving *is* the recovery (a duplicate, a replay, a refused transition — moving would itself be the failure); `BELOW_LIFECYCLE` for a failure handled entirely on the side-effect record. Collapsing these into one shape would have forced a fabricated movement onto a third of the register.
- **It fails in both directions, and the second is the point.** An unmarked unbuildable recovery fails the build; so does a marker on a movement that has since become buildable. Without the second, the honest escape hatch rots into the next `Pending` — a stale annotation nobody re-reads.
- **Found a third instance on its first run over migrated data.** `dp-fm-suppression`, already marked `Verified`, declares a consent re-check at despatch and therefore a `SCHEDULED -> SUPPRESSED` recovery no transition performs — and `dp-t06`, the only exit from `SCHEDULED`, carries that same re-check as its guard, so the record has nowhere to go at all. A validator that only re-confirms known defects has not earned anything; this one found one in a mode that was already signed off.
- **Prose is derived, not deleted.** `describeRecovery` renders the structured field back into the register and the system pages, collapsing genuinely chained movements into one path and separating alternatives with `·` rather than "then" — a low-confidence judgment reaches a person from `NORMALIZED` *or* from `REPLIED`, never both in order.
- **Limits (recorded, not hidden):** it checks recoveries, never guards. The `SCHEDULED` dead-end above was found by reading and is pinned by an explicit test rather than by the mechanism, and a guard that can never be satisfied remains invisible to it. It also cannot tell that a declared movement is the *right* one — only that the graph can perform it, so a recovery pointed at a real-but-wrong state passes.
- **Reusable for 2–6:** it already runs on all six. Any future system inherits the check the moment it declares a failure mode.

### 21. Escalation is a sequence, not a level — a timeout must know who was already asked
- **Earned:** cp-fm-approval-timeout package, 2026-08-27
- **Implementation:** `lib/engine/handlers/call-to-proposal.ts` (`nextAuthorityAbove`, `handleApprovalAttentionTimeout`, the assignment facts written by the routing step) · `data/profiles/kestrel/profile.ts` (`kestrel-proposal-approval-window`, `proposalApprovalTimeoutHours`)
- **Tests:** `tests/call-to-proposal-approval-timeout.test.ts` (13 tests; 9 targeted mutations each separately confirmed to fail it — at-or-above instead of strictly-above next authority, saturating at the top of the ladder instead of returning null, giving an unresolved assignment a ceiling anyway, a one-tick window boundary slip, addressing the escalation to the unresponsive approver, letting the timeout set a lifecycle transition, anchoring idempotency on the check rather than the condition, reporting an unowned draft as a late reviewer, and dropping the routing clock. None survived; the file was restored byte-for-byte and verified by SHA-256.)
- **Establishes:** Lead Rescue's attention timeout (`lr-fm-approval-timeout`, carried by #3's durable wait/resume machinery) escalates to an authority LEVEL, which is correct there because nothing was ever assigned to a particular person. Canon for Call-to-Proposal says "escalate to the NEXT approver in the authority chain", and "next" is only meaningful relative to whoever was already asked. Deriving the target from the assignee's own ceiling makes escalating a person to themselves structurally impossible — the qualifying set at `ceiling + 1` cannot contain a role whose ceiling is `ceiling`. Notifying the person who is already not responding is a no-op wearing the costume of an action.
- **The type system forced the honest branch.** `AuthorityLevel` is a closed union with no rung above 4, so "this approver is already the final escalation point" cannot be expressed as a level and had to become its own verdict: the chain is recorded as exhausted and **nobody is notified**, because the only person reachable is the one already asked. An empty escalation is not a quiet success.
- **"Nobody" is an answer that changes the escalation, not a blank to fill.** `cp-fm-approval-timeout` declares two causes — an unavailable reviewer, and *no named approver assigned at routing*. Implementing the declared prevention faithfully surfaced that Kestrel's own roles tie at the required approval authority, so `resolveEscalationOwner` (#16's honest-ambiguity rule) names nobody and the second cause is Kestrel's standing condition, not a hypothetical. The overdue report says the draft was never assigned rather than that a reviewer is late — a different sentence about a different problem, and the only truthful one.
- **HOLDS_POSITION is structural here, not promised.** No branch sets `transitionTo`, so the engine's transition-legality gate is never invoked and there is no lifecycle move for it to authorise or refuse. A mutation adding `transitionTo: 'APPROVED_SENT'` — a *legal* move under cp-t12, which is what makes the test meaningful — failed four assertions.
- **It bought zero transition coverage, by construction, and that is worth publishing.** Closing this failure mode moved Call-to-Proposal 8 → 8 of 18, because a mechanism that deliberately makes no lifecycle move cannot register on a metric that counts lifecycle moves. #20's number measures inspectability of the transition graph; it is silent about the correctness work that happens between transitions, and this is the first package to demonstrate that silence rather than assert it.
- **Limits (recorded, not hidden):** the escalation is a page-level notification like every other in this repository — no pager, inbox, or webhook, so "escalated" means recorded and rendered, not delivered. The clock is scenario-authored, never a real scheduler: nothing sweeps `AWAITING_APPROVAL` drafts on its own, and Call-to-Proposal is not wired into the durable wait-incident store that gives Lead Rescue its cross-process resumption. And the approver is a ROLE, never a person — the profile carries no individuals, so "named approver" is as specific as this data model can truthfully be.
- **Reusable for 2–6, but nothing currently claims it — corrected same day.** This line first read "Client Onboarding's readiness sign-off is the obvious next taker", which was wrong and was caught by checking rather than by review: Client Onboarding declares no human-attention failure mode at all (`co-fm-timeout` is a technical resource-creation timeout, `MOVES` to NEEDS_HUMAN). Only two `HUMAN_APPROVAL_TIMEOUT` failure modes exist portfolio-wide, and both are now closed. The shape — `resolveEscalationOwner(profile, assigneeCeiling + 1)` plus a routing-time assignment fact — needs nothing Call-to-Proposal-specific, but taking it up in a third system means ADDING a failure mode to canon, which is a modelling decision for whoever owns the canon, not an inheritance. #22 exists because this claim was made without checking, and now nothing can make it again.

### 22. A state you can enter and never be forced out of — asked of the graph, not of the reviewer
- **Earned:** parked-state attention package, 2026-08-27
- **Implementation:** `lib/proof/parked-state-attention.ts` (`auditParkedStates`, `abandonableStateIds`) · `data/parked-state-attention.ts` · `RecoveryPathSchema.holdsAt` and two new `validateLifecycle` checks in `lib/model/system.ts`
- **Tests:** `tests/parked-state-attention.test.ts` (15 tests; 9 targeted mutations each separately confirmed to fail it — collapsing the two-part condition to an either, dropping each half, counting a bounded judgment as the system acting, checking attention per-system instead of per-state, dropping WAITING states, leaving order to declaration, and disabling each of the two new validator checks. One survived the first suite and was repaired, not explained.)
- **Establishes:** `validateLifecycle` already refuses a `DEAD_END_STATE` — a non-terminal state with no outgoing transition. This is its subtler sibling, which that check passes cleanly: a state with several declared exits, **every one of which requires a `HUMAN_DECISION`**. On the graph it is not a dead end; in practice it is, because the only thing that can move the case is the party the case is already waiting on. The defect is never either half alone — it is `no self-driven exit AND no declared attention mechanism`, which is a place work can enter, sit forever, and have canon say nothing about it.
- **Prose became data, for the second time and the same reason.** `RecoveryMoveSchema` replaced free prose because "a validator cannot check a sentence". `HOLDS_POSITION` still carried only a `note`, so "holds position *where*" was unanswerable and no audit could tell a covered state from an uncovered one. `holdsAt` is now declared, validated to resolve, and **required** for `HUMAN_APPROVAL_TIMEOUT` — an attention claim that declines to say where it applies cannot be checked, and this repository does not make uncheckable claims.
- **It immediately found a live canon/code contradiction that 969 tests could not see.** `lr-fm-approval-timeout` declared `shape: 'MOVES'` (`NEEDS_HUMAN -> ESCALATED`) while its own `verificationTest` said "without transitioning lifecycle state", the handler's doctrine said never setting `transitionTo` "is the entire point", and the note under that very `MOVES` said "it never decides the case". Nothing caught it because the movement is genuinely buildable — a PERSON performs `lr-t23`; the timeout never does — so `validateLifecycle` passed. Corrected to `HOLDS_POSITION`, with the correction recorded in the note rather than silently applied.
- **Four states published, not summarised.** `dormant-pipeline-recovery/NEEDS_HUMAN`, `call-to-proposal/NEEDS_HUMAN`, `client-onboarding/NEEDS_HUMAN`, `owner-revenue-intelligence/AWAITING_OWNER_DECISION`. Being listed is not "the system is broken" — it is "a case can enter here and nothing in canon says what happens if it is never touched again".

- **Limits (recorded, not hidden):** it is a structural audit of what canon SAYS, never of what the code does — a system could declare a beautiful attention mechanism and implement none of it, and this would report it as attended. `DETERMINISTIC_RULE` is used as the proxy for "the system can act on its own", which is true of every timeout, budget and due-date exit in this repository today but is a property of the mechanism vocabulary rather than a proof. ### 23. A guard enforces the claim its own executor exists to make
- **Earned:** remote execution boundary package, 2026-08-27
- **Implementation:** `lib/ports/webhook-side-effect-executor.ts` (`isRemoteProofSafeEndpoint`, `WebhookSideEffectExecutor`) · `lib/config/side-effect-executor-config.ts` (`webhook` mode) · `lib/engine/wait-resume.ts` (`attachExecutionReceipt`) · `scripts/remote-execution-proof.ts` · `scripts/remote-execution-readback.ts`
- **Tests:** `tests/webhook-side-effect-executor.test.ts` (38) · `tests/execution-receipt-retention.test.ts` (6) · `tests/remote-execution-evidence.test.ts` (11); 8 targeted mutations of the executor each separately confirmed to fail — disabling the loopback guard, allowing plaintext, allowing credentials in the URL, granting retry permission for an unknown transport failure, treating a 5xx as a clean failure, treating a 409 as a clean failure, inventing a missing receiver id, and dropping the idempotency key from the request. None survived; restored byte-for-byte and verified by SHA-256.
- **Runtime artifact:** `n8n/evidence/lead-rescue-remote-execution.json` — an authorized notification left this machine over HTTPS, was accepted by an n8n Cloud workflow, and the delivery was read back from n8n's own execution log through a separate authenticated channel. Receiver execution `4`, carrying idempotency key `notify:lead-remote-proof-dispatch-timeout-1:dispatch-overdue`.
- **Establishes:** `SmtpSideEffectExecutor` refuses a ROUTABLE recipient, so it can never reach a real person. `WebhookSideEffectExecutor` refuses a NON-ROUTABLE endpoint, so it can never be satisfied by something on this machine. The two guards are inverses, and neither is a style preference: **each one enforces the exact claim its executor exists to support.** A remote-execution executor that could be pointed at loopback would make "the side effect left this machine" unfalsifiable — the guard is what turns the claim into one that could fail.
- **Certainty is earned, not defaulted.** `FAILED_BEFORE_EFFECT` is a PERMISSION — every layer above reads it as "a retry is safe". Over HTTP a receiver can act on a request it never answers, so the default is `OUTCOME_UNKNOWN` and only a provably pre-request failure (refused connection, unresolvable name, failed TLS handshake) earns retry permission. A 5xx and a 409 are both unknown, deliberately. The SMTP executor reached this rule the hard way, after a retained capture caught it granting retry permission for a post-DATA socket close that 39 green unit tests had missed; here it was applied from the first line.
- **A receipt you obtained and threw away is a receipt you do not have.** The first remote capture reported `receiverReportedExecutionId: null` for a send that had genuinely succeeded: `checkWaitIncident` resolved the counterparty's identifier and dropped it, leaving no link between our record and theirs. `attachExecutionReceipt` retains it, and is a SEPARATE function from `downgradeEffect` because that one documents itself as "strictly a downgrade path, never an upgrade" — folding provenance into it would put an upgrade-shaped branch inside the one function documented as unable to contain one. Tests pin that it cannot change `status` even when asked to.
- **The attestation is bounded by a check, not by trust.** No receiver API credential exists in this repository, so the independent read-back is fetched by an operator and merged by `remote-execution-readback.ts` — which REFUSES unless the attestation names the same execution id and the same idempotency key the application independently recorded. The artifact can never carry a read-back that does not correspond to the delivery beside it, and `doesNotProve` states plainly that the fetch is attested rather than automated.
- **Limits (recorded, not hidden):** the counterparty is a workflow endpoint, never a customer — nothing on this path forwards to a person. The endpoint guard inspects the URL, not DNS, so a public hostname resolving privately would pass it. The deployed Vercel application is NOT configured for this mode; the crossing was made by the application running locally. And `attemptVerify` still throws: the receiver records deliveries but exposes no lookup by idempotency key, so an `OUTCOME_UNKNOWN` on this path cannot yet be narrowed.
- **Reusable for 2–6:** the executor is system-agnostic and selected by the shared composition root; any system whose runtime resolves an executor inherits it by configuration alone.

### 24. Who is accountable is a fact a business knows, not an inference from rank
- **Earned:** declared accountability package, 2026-08-27
- **Implementation:** `lib/model/profile.ts` (`accountabilities`, `resolveAccountableRole`, four new `validateProfileConsistency` checks) · `lib/engine/handlers/call-to-proposal.ts` (`resolveApprovalAssignment`, `PROPOSAL_APPROVAL_ACTION`) · `data/profiles/kestrel/profile.ts`
- **Tests:** `tests/accountability.test.ts` (13) plus the extended approval-timeout suite; 7 targeted mutations each separately confirmed to fail — asking rank before the declaration, ignoring the declared next approver, permitting a sideways "escalation", and disabling each of the four validators. Two survived the first pass and were repaired, not explained.
- **Establishes:** `resolveEscalationOwner` (#16) answers "who has ENOUGH AUTHORITY?" and rightly refuses to break a tie between equal roles. That left a different question unanswerable. Kestrel's Operations Coordinator and Finance both clear the proposal authority bar, and **neither of them approves proposals** — so asking rank returned an honest ambiguity where the business had a real answer all along, sitting in prose: the Client Partner "owns named accounts through … proposal", escalating to the founder who "approves all commercial commitments". Prose is not checkable. This makes it data.
- **It is not a tie-break relocated into configuration,** which #16's docstring rightly warns against. It ranks nothing and grants nothing: the accountable role's `authorityCeiling` is untouched, so naming somebody accountable can never give them authority they do not have, and despatch stays capped at authority 2 regardless. It records one fact — whose desk this lands on, and whose desk it goes to next.
- **Declared beats derived, and the order is load-bearing.** Rank is asked only when the business has said nothing. A mutation that asked rank first produced a confidently wrong name (an Operations Coordinator approving a commercial proposal) while every other test still passed.
- **A sideways handoff is not an escalation.** `ACCOUNTABILITY_ESCALATION_NOT_UPWARD` refuses an escalation target whose ceiling is not strictly higher. Permitting it would let a timeout report that a case was raised when it was merely moved — progress it did not make.
- **The mutation pass caught a test that checked the label instead of the behaviour.** On Kestrel the declared next approver and the rank-derived one AGREE (Client Partner ceiling 3 → founder either way), so a mutation ignoring the declaration survived. Repaired with a profile where the two DISAGREE by construction — declared skips a rank that derivation would stop at — which is the only shape that can tell them apart.
- **The honesty machinery did not soften.** The unowned-draft path — a business that has never decided, two roles tied — was Kestrel's own condition before this and is still fully proven, now on a synthetic profile. A fiction fixing itself must not be allowed to retire the mechanism that reported the problem.
- **Limits (recorded, not hidden):** it is one accountability per action per profile, with no notion of delegation, absence, or working hours; a named role that is on holiday is indistinguishable from one that is ignoring the case. The escalation chain is one hop — `escalatesTo` names a single next role, not a ladder.
- **Reusable for 2–6:** `resolveAccountableRole` is profile-level and action-keyed; any system can ask about its own action id without a schema change.
