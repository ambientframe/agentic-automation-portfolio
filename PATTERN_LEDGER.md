### 12. Durable write-ahead observation accounting, reconciled rather than counted
- **Earned:** observation integrity package, 2026-08-26
- **Implementation:** `lib/persistence/observation-intent-store.ts` · `lib/observability/observation-integrity.ts` · `lib/observability/lead-rescue-journal.ts` (composition root)
- **Tests:** `tests/lead-rescue-observation-integrity.test.ts` (20 tests, RED before implementation; 8 targeted mutations each separately confirmed to fail it) · `tests/observation-integrity-evidence.test.ts` (20 tests, each confirmed to fail against a deliberately corrupted artifact)
- **Runtime artifact:** `n8n/evidence/lead-rescue-observation-integrity.json` — the journal directory was made unwritable for exactly one real HTTP ingress; the business path returned `200 ACCEPTED` and durably parked the case, the observation was genuinely lost, and the runtime named it: `CONFIRMED_DROP`, with the recorder's own `EACCES: permission denied, mkdir …` as the reason.
- **Establishes:** a lossy recorder can be held to account without becoming blocking. A marker naming the intended observation is written BEFORE the record, removed after a success, and annotated-and-left after a reported drop; a marker still outstanding is reconciled against the journal by `journalEventId`, so a crash in the cleanup window is not mistaken for data loss and a genuinely missing record cannot hide. The three answers stay distinct — `NO_KNOWN_LOSS`, `KNOWN_LOSS`, `UNAVAILABLE` — and an unreadable ledger or an unreadable journal both fail into the third rather than into the flattering first.
- **Why not a counter:** a process-local tally dies in exactly the crash it would need to survive, and reports a clean instrument at the moment the instrument is least trustworthy. The marker is durable, so the accounting outlives the process; `tests/lead-rescue-observation-integrity.test.ts` proves an unresolved intent survives a genuinely reconstructed store.
- **Limits (recorded, not hidden):** an observation whose marker ALSO failed to be written is invisible. That is why the clean answer is named `NO_KNOWN_LOSS` and never `COMPLETE`, why no completeness rate exists anywhere in the payload, and why the bound travels with every answer including the clean one. The `UNRESOLVED_INTENT` kind is test-proven; the retained capture exercises `CONFIRMED_DROP`.
- **Reusable for 2–6:** `withObservationIntegrity` decorates any `ExecutionJournalRecorder` and `deriveObservationIntegrity` reads any `ExecutionJournalReader`. Neither knows what a lead is.

### 14. A failure verdict that grants permission is earned structurally, never inferred from an error code
- **Earned:** execution-boundary classification package, 2026-08-26
- **Implementation:** `lib/ports/smtp-side-effect-executor.ts` — `SMTP_COMMANDS_BEFORE_DATA` plus the phase read in `attemptSend`'s catch
- **Tests:** `tests/smtp-side-effect-executor.test.ts` (39 tests, up from 17; 5 RED before implementation, and 5 targeted mutations of the shipped fix each separately confirmed to fail it — re-admitting the socket codes, adding `DATA` to the pre-DATA set, widening the syscall check, forcing the phase test true, and inverting the default)
- **Establishes:** `FAILED_BEFORE_EFFECT` is not a description of a socket, it is a **permission** — every layer above reads it as "nothing reached the recipient, a retry is safe." A permission may therefore only be issued where non-delivery is structural: a code that cannot follow DATA by protocol, a `connect` syscall, or an error raised against an SMTP command that precedes DATA. Everything else, including every unrecognised code and every error carrying no code at all, resolves to `OUTCOME_UNKNOWN` and parks for a person. The asymmetry is the point: a false uncertainty costs an operator one decision, a false certainty costs the customer a duplicate.
- **Why not a wider blocklist:** the first attempt routed every socket-class code to uncertainty. It was sound and it broke a genuine connection-refusal test, because nodemailer collapses connect-phase failures into `ESOCKET` — a real `ECONNREFUSED` arrives as `{code: 'ESOCKET', syscall: 'connect', command: 'CONN'}`. A blocklist that parks every refused connection trains an operator to clear a queue of decisions that were never theirs to make. Reading the phase the transport already reports is both sounder and more precise than either blanket rule.
- **The trap, recorded because it cost a full cycle:** a phase field is not necessarily a phase. nodemailer's `command: 'CONN'` marks a *connection-level* error whenever it occurs, not the connect phase — a server that takes the whole body and then destroys the socket reports `{code:'ECONNECTION', command:'CONN'}`, indistinguishable in shape from a greeting failure. Trusting it re-issued retry permission for exactly the case this pattern exists to stop, and 39 green unit tests did not notice. The re-captured runtime evidence did, on the first run. Before trusting any provider's phase field, probe it against the failure you actually fear.
- **Runtime artifact:** `n8n/evidence/lead-rescue-observation-integrity.json` — case D: the receiver holds 979 bytes and a stored message id, and the application records `OUTCOME_UNKNOWN` with verdict `DECLINED_TO_CLAIM`, parking the case rather than authorising a retry. Guarded by test 9b in `tests/observation-integrity-evidence.test.ts`, which ties each verdict to the bytes the receiver observed; 4 targeted corruptions each confirmed to fail it.
- **Limits (recorded, not hidden):** the phase is only as good as the transport's own reporting, *and* only as good as your understanding of what that reporting means. An adapter whose provider surfaces no trustworthy equivalent must fall back to the conservative rule and accept the extra uncertainty; it may not invent a phase.
- **Reusable for 2–6:** the shape generalises to every `SideEffectExecutor` any system adds. The question "does this failure prove non-execution, or merely suggest it?" is the same for a CRM write, an SMS gateway, and a calendar invite; only the phase evidence differs.

- **Earned:** dp-fm-wrong-entity package, 2026-08-26

- **Establishes:** consent, account status, and commercial eligibility are all questions about a SPECIFIC party. - **Limits (recorded, not hidden):** the guard only runs when the cycle supplies competing candidates. A record resolved upstream on a stable identifier has no ambiguity to decide, and manufacturing a decision for it would pad every run with a step that never chose anything — so a WRONG upstream resolution is invisible here. - **Reusable for 2–6:** every system that matches an inbound artifact to an account has this shape — Lead Rescue on contact identity, Receivables on invoice identity, Client Onboarding on the signed party. Only the identifier differs.

### 18. A declared recovery is a claim about the transition graph, so ask the graph
- **Earned:** lifecycle-recovery package, 2026-08-26
- **Implementation:** `lib/model/system.ts` — `RecoveryPathSchema`, `RecoveryMoveSchema`, `describeRecovery`, and the recovery checks inside `validateLifecycle` · all 43 failure modes across `data/systems/**`
- **Tests:** `tests/lifecycle-recovery.test.ts` (12 tests; 8 RED before implementation, and 10 targeted mutations each separately confirmed to fail it — short-circuiting the check, disabling each of its three issue kinds, checking only the first movement of a multi-step recovery, dropping a marker so a defect reads as handling, inventing the missing transition, pointing a real recovery at an undeclared state, pointing one at a forbidden move, and stripping the defect wording from the rendered prose. None survived.)
- **Establishes:** a failure mode's `terminalState` was free prose, and a validator cannot check a sentence — which is exactly why two Dormant Pipeline recoveries sat for months declaring movements the engine would have refused. Replacing it with `{from, to}` pairs turns "where does this end up" from a description into a question the transition graph can answer, for every failure mode in every system.
- **Three shapes, because recoveries genuinely have three.** `MOVES` for an ordered list of movements; `HOLDS_POSITION` for the cases where not moving *is* the recovery (a duplicate, a replay, a refused transition — moving would itself be the failure); `BELOW_LIFECYCLE` for a failure handled entirely on the side-effect record. Collapsing these into one shape would have forced a fabricated movement onto a third of the register.
- **It fails in both directions, and the second is the point.** An unmarked unbuildable recovery fails the build; so does a marker on a movement that has since become buildable. Without the second, the honest escape hatch rots into the next `Pending` — a stale annotation nobody re-reads.
- **Found a third instance on its first run over migrated data.** `dp-fm-suppression`, already marked `Verified`, declares a consent re-check at despatch and therefore a `SCHEDULED -> SUPPRESSED` recovery no transition performs — and `dp-t06`, the only exit from `SCHEDULED`, carries that same re-check as its guard, so the record has nowhere to go at all. A validator that only re-confirms known defects has not earned anything; this one found one in a mode that was already signed off.
- **Prose is derived, not deleted.** `describeRecovery` renders the structured field back into the register and the system pages, collapsing genuinely chained movements into one path and separating alternatives with `·` rather than "then" — a low-confidence judgment reaches a person from `NORMALIZED` *or* from `REPLIED`, never both in order.
- **Limits (recorded, not hidden):** it checks recoveries, never guards. The `SCHEDULED` dead-end above was found by reading and is pinned by an explicit test rather than by the mechanism, and a guard that can never be satisfied remains invisible to it. It also cannot tell that a declared movement is the *right* one — only that the graph can perform it, so a recovery pointed at a real-but-wrong state passes.
- **Reusable for 2–6:** it already runs on all six. Any future system inherits the check the moment it declares a failure mode.

- **Implementation:** `lib/ports/webhook-side-effect-executor.ts` (`attemptVerify`, `readJsonObject`, `lookupEndpoint` guard) · `lib/config/side-effect-executor-config.ts` (`WEBHOOK_LOOKUP_ENDPOINT_ENV_VAR`) · `n8n/workflows/lead-rescue-delivery-log.json` · `n8n/workflows/lead-rescue-delivery-lookup.json`
- **Tests:** `tests/webhook-verification-lookup.test.ts` (33); 6 targeted mutations each separately confirmed to fail — truthiness instead of strict identity on `found`, dropping the mismatched-key guard, ceasing to distinguish a 5xx from an inconclusive answer, inventing an external id the receiver never gave, honouring a receiver that claims a confirmed negative, and turning the read-only query into a write. None survived; the file was restored byte-for-byte and verified by MD5.
- **Establishes:** `attemptSend` has always refused to grant retry permission it had not earned, which left every `OUTCOME_UNKNOWN` permanently open because the receiver exposed no way to ask about a specific operation. `attemptVerify` threw — honest and useless in equal measure. It can now narrow one, in one direction.
- **The asymmetry is the pattern.** A record found is `CONFIRMED_EXECUTED`. A record absent is `STILL_UNKNOWN`, always, and never `CONFIRMED_NOT_EXECUTED`. A receiver cannot prove it never received something: a request can be accepted at the socket and die before the first write to its log, which is precisely the failure that produced the unknown being investigated. A receiver that volunteers that its log is complete is not believed either — it cannot observe what it failed to record, so the claim is not evidence. `CLAUDE.md` already stated the rule; this is its first application to an external provider's answer.
- **Half is the useful half.** The dangerous error is sending twice, and confirming an effect DID happen is what prevents it. Confirming one did not merely grants retry permission, and a retry left unpermitted is safe. A design that could only narrow negatives would be worth much less.
- **An answer about another operation is worse than no answer**, so the key echo is checked before `found` is read and a mismatch can never reach the confirming path. The lookup workflow therefore echoes the key from the request rather than from the matched row — read from the row it would be absent on a miss, and the executor would reject its own answer as being about an unknown operation.
- **"Could not run" and "ran and settled nothing" stay different facts.** Transport failure and 5xx throw, which `resolveVerify` turns into `UNAVAILABLE`; every answer the receiver actually gave that fails to establish anything is `STILL_UNKNOWN`. Collapsing the two would report an outage as an inconclusive check.
- **The lookup endpoint carries the send endpoint's guard**, and a misconfigured one fails the whole selection closed rather than being dropped — silently discarding it would leave sends running with verification the operator believes is configured and which is not there.
- **PROVEN LIVE, 2026-08-28.** Both workflows are deployed and active on a real n8n instance (`1onJs9j9KaG07FXc`, `yLdQ6yKw7p1YlZUk`), writing to and reading a data table this application holds no credential for. `scripts/remote-verification-proof.ts` drove the real executor across the public internet: a delivery returned `SUCCEEDED` with n8n's execution id `8`, a lookup of that key returned `CONFIRMED_EXECUTED` carrying **the same id the receiver reported**, and a key never sent returned `STILL_UNKNOWN`. Retained at `n8n/evidence/lead-rescue-remote-verification.json`, guarded by `tests/remote-verification-evidence.test.ts` (13 assertions; 6 deliberate corruptions each confirmed to fail it — inventing an external id, upgrading the absent key to a confirmed negative, claiming the receiver held the absent record, relocating the receiver onto this machine, trimming the limits, and rewriting the unconfigured refusal as a success).
- **The asymmetry survived contact with a real receiver, which is the part worth having.** n8n answered `found: false` for the never-sent key with HTTP 200 and complete confidence. The executor still returned `STILL_UNKNOWN`. That refusal is easy to hold against a stub and easy to lose against a provider that sounds certain, so it is captured as a fact rather than an assertion.
- **Three assumptions were settled by running it**, all of which had been recorded as unverified: the `found` expression returns a real boolean, `alwaysOutputData` yields an answer on a miss instead of hanging until timeout, and the lowercase `idempotency-key` header is what reaches the receiver. The miss case also echoes the requested key, which is what stops the executor discarding its own answer as being about an unknown operation.
- **Limits (recorded, not hidden):** this does **not** make Lead Rescue live for a client. No customer exists, every input was authored here, and the receiver forwards nothing to anyone — no email, SMS, CRM write, or onward webhook, verified by node-type audit before activation. It proves one confirmable delivery and one honest unknown, not exactly-once delivery across arbitrary crash modes. It was produced by the application running on this machine; the hosted build has no lookup endpoint configured. Durability beyond the moment of capture is unproven — the lookup ran seconds after the delivery.
- **SURFACED 2026-08-28, because a capability a buyer cannot see is one the artifact does not have.** For a day this was the strongest integration evidence in the repository and appeared on **no rendered surface**: `remote-verification` existed in a script, an artifact, and a test, and in nothing under `lib/` or `app/`. The fidelity ledger now carries a `remote-verification` row derived from the capture through `readRemoteVerificationEvidence`, and the prerendered `/lead-rescue` page states the receiver's own execution id and the standing refusal in the buyer's own reading. **The row is REAL only on a conjunction:** a confirmation carrying the receiver's identifier AND a never-seen key that still came back `STILL_UNKNOWN`. A capture showing a confident confirmed-negative is not weaker evidence — it is evidence the boundary lied, and reading the confirmation half while ignoring the rest is precisely how a proof surface flatters itself. 5 mutations confirmed to fail; **one survived first time and was a genuine hole** — the "boundary lied" test moved two fields together and so could not isolate which was load-bearing, which is now a separate case asserting that the recorded verdict outranks the capture's claim about its own guarantee.

### 31. Verbatim evidence must travel through a channel that cannot reformat it
- **Earned:** three-profile registration package, 2026-08-28
- **Implementation:** `docs/PROFILE_AUTHORING_PACKET.md` §8 (snippet written to `data/profiles/<slug>/registration.snippet.ts`, not to a report) · `data/profiles/index.ts` · `docs/evidence/grounding-captures.json`
- **Tests:** 4 mutations each separately confirmed to fail — one word changed inside a captured quote, an `establishes` claim edited after capture, a grounded demonstration relabelled `STRUCTURAL_FIXTURE`, and a profile's revenue mix no longer summing to 100. No survivors; both files restored byte-for-byte and verified by SHA-256. The capture gate itself then re-fetched all 34 sources live and located every quote.
- **Establishes:** three finished, independently verified profiles sat unregistered for a working day because their registration snippets reached this repository **only inside PDF-converted markdown**. That conversion split every `fi`/`fl` ligature (`profile` → `pro fi le`, `verified` → `veri fi ed`) and collapsed line breaks into double spaces. The quotes were therefore no longer verbatim and could not pass capture — **through no fault of the authors, whose originals were exact.**
- **The failure is in the channel, not at either end.** Both the author and the gate were behaving correctly. A report is prose, and every pipeline that touches prose feels licensed to improve it — ligature substitution, smart quotes, hyphenation, whitespace collapsing. Evidence whose value is that it is byte-exact cannot survive a medium whose job is to render nicely.
- **The fix is to change the channel, never to repair the payload.** The recorded plan had been to de-corrupt the quotes by hand and let the gate adjudicate the repair. That would have worked and it was the wrong instinct: it treats a lossy channel as a fact and makes a model's reconstruction part of the evidence chain. The `.rtf` export of the same three handbacks was sitting beside each PDF, carried the text unmodified, and captured first time. **Look for a less-processed copy before reconstructing anything.**
- **Extraction over transcription.** The snippets were pulled out of the handbacks by script and spliced in mechanically, because a model retyping a quote into its own output is the same class of lossy channel that caused the problem. Nothing verbatim was routed through generated text.
- **The generalisation:** a verbatim quote, a hash, a key, a diff, a signature. Each is worthless if altered and each looks fine after alteration. Route them through git, or a file, or anything that treats bytes as bytes — and never through a summary, a report, a chat message, or a rendered document.
- **Limits (recorded, not hidden):** nothing mechanically enforces the new packet rule. An author can still paste a snippet into a report, and the failure mode reappears — visibly and at capture time rather than silently, but it reappears. The `.rtf` recovery also worked by luck of that export existing; had only the PDF survived, reconstruction would have been the only route and the gate would have been the only check on it.
